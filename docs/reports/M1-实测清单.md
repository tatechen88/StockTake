# M1 游戏内实测清单（StackLedger）

> 目的：冻结规划第三章 B 的 4 项未定事实，并验收 `/sl diag` 自检输出。
> 执行方式：进入游戏（正式服 12.1.x），**逐条**把命令输入聊天框，把输出回传。
> 记录原则：原样保留输出（含 nil / 报错），不要"看着差不多"就跳过——M1 的价值就是消灭猜测。

---

## 0. 前置

1. 插件已放入 `Interface\AddOns\StackLedger\`，角色选择界面"插件"按钮里能看到 **堆叠账本 StackLedger** 且无红色依赖报错。
2. 进游戏后执行 `/sl diag`，把聊天框输出**整段**复制回来（它会同时写入 `SL_DB.diag`）。
3. 打开一次银行（角色银行 + 战团银行页面都点一遍），再执行一次 `/sl diag`。

## 1. 枚举成员核对（规划 A-4 / A-5）

```lua
/dump Enum.BankType
/dump Enum.BagIndex
```

**期望**
- `Enum.BankType` = `{ Character = 0, Guild = 1, Account = 2 }`
- `Enum.BagIndex` 中出现命名成员：`Keyring`(-1)、`CharacterBankTab`(-2)、`AccountBankTab`(-3)、`BankBag`(-4)、`CharacterBankTab_1..6`(6..11)、`AccountBankTab_1..5`(12..16)、`ReagentBag`(5)
- **失败判据**：任一命名成员不存在 → 立即回传，需改回数值兜底（但这会让代码变脆，需 Lead 决策）

## 2. 银行页动态枚举（规划 A-3，M1 第 1 项）

```lua
/dump C_Bank.FetchPurchasedBankTabIDs(Enum.BankType.Character)
/dump C_Bank.FetchPurchasedBankTabIDs(Enum.BankType.Account)
/dump C_Bank.FetchNumPurchasedBankTabs(Enum.BankType.Character)
/dump C_Bank.FetchNumPurchasedBankTabs(Enum.BankType.Account)
/dump C_Bank.FetchPurchasedBankTabData(Enum.BankType.Character)
```

**期望**：Character 返回你**已购买**的角色银行页 ID 数组（元素属于 6..11）；Account 返回战团页 ID 数组（元素属于 12..16）；未购买战团页时 Account 可能为空数组 → 空数组不算失败，但**要记录**。
**关键回归点**：返回值必须是**已购买**的集合（例如你只买了 3 页，就该只返回 3 个元素）——这证明"不依赖硬编码 6..11 全扫"的设计成立。

**要回答的问题**

## 4. 战团银行槽位与事件（规划 A-7，M1 第 2/3 项）

打开战团银行页，往里面放进/取出一件物品，观察聊天框是否出现自检日志（`SL_DB.diag` 会记录事件名）。若没日志，手动确认：

```lua
/dump C_Bank.CanViewBank(Enum.BankType.Account)
/dump C_Bank.FetchDepositedMoney(Enum.BankType.Account)
```

**期望**：`CanViewBank(Account)` 为 true；存取物品时触发 `PLAYER_ACCOUNT_BANK_TAB_SLOTS_CHANGED`（或至少 `BAG_UPDATE` 命中战团页 bagID）。
**若事件不触发**：记录实际触发的事件名（可用 `/eventtrace` 观察），Lead 需要据此调整 Scanner_Warband 的事件绑定。

## 5. GetItemCount 五参对照（规划 A-1，M1 第 3 项）

先随便拿一件背包里的物品，鼠标悬停看 tooltip 的"背包/银行/战团"数字，然后：

```lua
/run local id = C_Container.GetContainerItemInfo(0,1).itemID; print("id", id, "bags", C_Item.GetItemCount(id), "withBank", C_Item.GetItemCount(id,true), "withReagent", C_Item.GetItemCount(id,true,false,true), "withAccount", C_Item.GetItemCount(id,true,false,true,true))
```

**期望**：`withAccount` ≥ `withReagent` ≥ `withBank` ≥ `bags`，且 tooltip 里"本角色合计"与其中合适的一档一致。
**要回答**：`includeAccountBank=true` 是否**真的**把战团银行算进去了（把一件物品只放进战团银行、背包清空，看 withAccount 是否 ≥1）。这条决定 Counter 是否可以用它做校准。

### 5b. 用 `/sl diag` 做自动对照（**v1.2 已对齐口径，这是首选方式**）

对抗审计发现旧版 diag 的对照口径错位（本地含装备不含战团 ↔ API 不含装备含战团），差值恒为 `warband − equip`，会让本条实测失去意义。**现已修复**，口径冻结为：

```
本地合计 = bags + bank + reagent + warband      （与 C_Item.GetItemCount(id,true,false,true,true) 对齐）
equip    = 单列展示，不参与差值
期望 diff = apiCount − localCount == 0
```

执行 `/sl diag`，看第 3 项的两行输出：
```
3) 背包首件 N：本地 bagsA + bankB + reagentC + warbandD = Y
3) C_Item.GetItemCount(5参)=Z，差=D —— 应为 0（口径已对齐，非 0 即扫描或 API 行为异常）；equip=E 单列不参与差值
```
**判读**：
- `差 = 0` → 本地扫描与官方 API 完全一致（**最理想**）；
- `差 ≠ 0` → 回传 `SL_DB.diag.countCompare`（含 `localBreakdown` 五项 + `equipCount` + `diff` + `aligned`），这是真问题；
- API 不可用时输出 `n/a`，不算失败，但要记下来（说明 12.x 上该函数可能又被改动）。

**建议做两次**：一次拿普通物品（背包里），一次拿**只放在战团银行**的物品——后者是 `includeAccountBank` 是否真的生效的关键证据。
